# Политика безопасности

## Поддерживаемые версии

Исправления безопасности выпускаются для последней стабильной версии Gildra DSH. Старые версии следует обновить перед диагностикой проблемы.

## Как сообщить об уязвимости

Не публикуйте секреты, ключи, приватные адреса серверов или рабочий код в обычном issue. Создайте приватное сообщение через [GitHub Security Advisories](https://github.com/Gildra-Foundation/dsh/security/advisories/new).

Укажите:

- затронутую версию и операционную систему;
- минимальные шаги воспроизведения;
- возможное влияние;
- безопасный пример или журнал без credentials;
- предложенное исправление, если оно есть.

Мы постараемся подтвердить получение в течение трёх рабочих дней. Публичное раскрытие согласовывается после появления исправления или безопасного обходного решения.

## Модель доверия загрузок

Каждый скачиваемый артефакт защищён одним из двух механизмов — и мы явно
называем, каким именно, вместо общего «всё проверяется»:

| Артефакт | Идентификатор | Проверка целостности |
| --- | --- | --- |
| Node.js (5 платформ) | версия в `kit.json` | SHA-256 из `kit.json` |
| Ollama (Linux) | версия в `kit.json` | SHA-256 из `kit.json` |
| Исходники DeepSeek Harness | commit SHA в `kit.json` | только TLS + пин коммитом¹ |
| CodeGraph | commit SHA в `kit.json` | только TLS + пин коммитом¹ |
| npm-плагины профиля | точные версии | `pnpm-lock.yaml` (integrity) + карантин новых релизов + sentinel-преаудит |
| GitHub-плагины профиля | commit SHA в спеке | пин коммитом; у части записей lock нет integrity-хеша² |
| Модель Ollama `nomic-embed-text` | имя (mutable-тег)³ | нет |
| Language servers | точные top-level версии | транзитивные зависимости не зафиксированы³ |
| Обновления кита | тег релиза | SHA-256 из `SHA256SUMS.txt` того же релиза |
| Skills из GitHub | commit SHA (резолвится установщиком) | SHA-256 содержимого показывается пользователю до установки |

¹ GitHub не гарантирует байтовую стабильность автогенерируемых архивов
(`codeload`), поэтому фиксация их SHA-256 в манифесте ломала бы установки при
смене компрессии на стороне GitHub. Пин по commit фиксирует содержимое
логически; целостность канала обеспечивает TLS. Это осознанный компромисс, а
не упущение.

² `pnpm` записывает `integrity` не для всех git-hosted записей; недостающие
хеши появятся при следующей регенерации lock, если upstream начнёт их
публиковать стабильно.

³ Известные незакрытые места. Не заявляем их «проверенными»; закрытие
запланировано (дайджест модели, lock для LSP).

## Изоляция пользователей и сессий (Gildra Runtime)

- **Изоляция людей = Unix-права.** На сервере каждому сотруднику соответствует
  отдельный Unix-пользователь: SSH-ключи, Git-credentials и config, DSH_HOME,
  RAG-индекс, state Runtime, worktree-воркспейсы, токены и история — в его
  домашнем каталоге. Общих каталогов с credentials команды не существует;
  Runtime создаёт state/каталоги с правами 0700, файлы — 0600.
- **Одна write-сессия — один Git worktree** и собственная ветка
  `session/<user>/<id>`; путь строит только сервер из валидированных
  идентификаторов. Прямая запись в защищённые ветки (`main`, `master`,
  `production`, `release/*`) закрыта на уровне Workspace Manager; объединение —
  только через merge workflow с явным действием.
- **Write-lease с owner-token**: чужой активный lease нельзя ни забрать, ни
  снять; перехватывается только доказуемо осиротевший (мёртвый PID или
  протухший heartbeat). Cleanup завершает только процессы, зарегистрированные
  за сессией (PID/process group) — не по совпадению подстроки пути.
- **API Runtime (/gildra/v1/*) слушает только loopback**, мутации требуют
  same-origin и owner-token сессии; произвольные shell-команды через API не
  выполняются. Audit-лог пишет только идентификаторы и факты — без секретов,
  токенов, env и содержимого кода.

## Границы доверия

Особенно важны сообщения об updater, установщиках, Host RPC, SSH-туннелях, синхронизации конфигурации, установке Skills/плагинов и обходе подтверждений. Пользовательские проекты, токены, SSH-ключи и истории сессий не должны попадать в репозиторий или диагностические архивы.
