# Релиз Gildra DSH

Выпуск = согласованный бамп версии в нескольких местах + зелёный CI + тег,
совпадающий с манифестом. Архивы собирает только тег; push в `main` публикует
лишь конфигурацию.

## Места синхронной правки версии (все обязательны)

1. `config/kit.json` → `distribution.version` — источник истины.
2. `scripts/kit-config.test.mjs:26` — растяжка `assert.equal(...версия...)`;
   обнови значение (падение здесь при бампе — задумано).
3. `CHANGELOG.md` — перенеси содержимое `[Unreleased]` в раздел новой версии с
   датой, обнови ссылки сравнения внизу файла. Не копи несколько версий в
   Unreleased.
4. `README.md`, раздел «Состояние сборки» — номер кандидата и что проверено.
5. `docs/release-audit.md` — новый аудит по образцу существующего: таблица
   пройденных пользовательских путей + раздел «Намеренно не выполненные
   внешние действия».

**Не правь** `desktop/macos/Info.plist` — версии в нём перезаписывает
`build.sh` из манифеста, а ручная правка создаёт ложный diff.

Если с прошлого релиза менялся `plugins/gildra-dsh-ui-compact/lib/client.js` —
подними `version` в `plugins/gildra-dsh-ui-compact/package.json`, иначе браузер
пользователей продолжит держать старый клиент в кэше.

## Порядок выпуска

1. Все правки выше → `./scripts/verify.sh` (он сверяет версию собранного .app с
   манифестом — рассинхрон падает локально, а не на CI).
2. Коммит в `main`, дождись зелёного CI.
3. Release-gate: синхронизация управляемого профиля на настроенные серверы
   (`node scripts/sync-server-fleet.mjs --repo-dir <репо> --install-root
   ~/.gildra-dsh`) — по README она обязательна перед тегом.
4. Тег строго `v<distribution.version>` (например `v0.1.16`). `release.yml`
   сверяет тег с манифестом на всех трёх платформенных джобах и падает при
   расхождении. Тег создаёт архивы и `SHA256SUMS.txt` — этот файл читает
   апдейтер, без него обновление из приложения не работает.

## Чего не делать

- Не создавай тег без явной просьбы пользователя — по `CONTRIBUTING.md` выпуск
  делает maintainer после проверки; твоя работа заканчивается на готовом
  коммите и отчёте.
- Не помечай в release-audit сценарии «пройденными», если ты их фактически не
  выполнял — раздел намеренно различает проверенное и не запускавшееся.
